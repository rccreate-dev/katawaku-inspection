# 運用メモ(責任者・管理者向け)

DEPLOY.md は初回の設置手順、このファイルは「動き始めたあと」の運用で気をつける点です。
(SPEC 版1.4 §2.15・§5.4.4・§7.3 に対応)

## 1. スプレッドシートを直接編集したときの反映時間

| シート | 直接編集の反映 |
|---|---|
| **Config(設定)・Items(項目マスタ)・Sites(現場)** | **約1分後(最大60秒)** |
| Users・Devices・Assignments・Memberships・Absences(名簿・端末・担当・参加・不在) | すぐ(次の操作から) |
| Records・RecordItems・Photos・Notes・Events・Idem・Invites・Reports | すぐ(通常は手で編集しない) |

- **Config / Items / Sites を直接編集したら、反映まで約1分かかります。** 編集した直後に画面を開いても、古い設定(例: 写真の上限枚数、項目の文言、現場の状態)が表示されることがあります。1分ほど待ってから、アプリを開き直してください。
- 名簿(Users)・担当表(Assignments)・不在(Absences)・端末(Devices)の変更は遅れません。ユーザーの停止、担当の外し、端末の登録解除は次の操作から効きます(権限の判定にはキャッシュを使いません)。
- 現場の「合言葉(joinKey)」は遅れません。アプリの「合言葉を更新」でも、シートで直接書き換えても、更新後すぐに古い合言葉は使えなくなります。
- 急いで反映させたいとき: Apps Script のエディタで関数 `clearRefCache` を選んで「実行」すると、キャッシュをすぐ捨てます(再認可の画面は出ません。ログに「OK」と出ます)。
- 現場を閉鎖(`status=closed`)した直後の約1分間は、まだ記録の作成が通ることがあります。確実に止めたいときは1分待ってから現場の運用を止めてください。
- アプリが書き込む設定(例: 現場の写真フォルダIDの初回記入、合言葉の更新)は、書いた直後にキャッシュを捨てるので遅れません。

## 2. バージョン1.4への更新手順(写真送信の高速化)

1. Apps Script のプロジェクトに、新しいファイル **`RefCache`**(`RefCache.gs`)と **`PhotoUpload`**(`PhotoUpload.gs`)を追加し、`backend/` の中身を貼る。
2. 既存の `Code` `Repo` `Schema` `Seed` `Photos` `Admin` `Membership` を `backend/` の最新の中身で上書きする(DEPLOY.md の3-3のファイル一覧は、この2ファイルを加えた16ファイル)。
3. エディタで `setupSheets` を1回実行する。Config に不足している設定 **`photoSingleMaxChars`(1200000)** と **`photoParallel`(3)** の行が追記される。**既存の行・値は上書きしない**ので、設定済みの値は変わらない。実行しなくても、値が無いときは既定値で動く。
4. 「デプロイを管理」→ 既存のデプロイを編集 → バージョン「新バージョン」→ デプロイ(**URLは変わらない**)。
5. 写真を1枚撮って、送信が数秒で終わることを確認する。

## 3. 写真まわりの設定(Config)

| キー | 既定 | 意味・注意 |
|---|---|---|
| `photoSingleMaxChars` | 1200000 | 1枚を1回で送るときのデータ(base64)の最大文字数。4の倍数。`photoMaxBytes` を上げるときは `ceil(photoMaxBytes ÷ 3) × 4` 以上にする(例: 800000バイト → 1066668 以上)。下回っても動くが、アプリが小分け送信になって遅くなる |
| `photoParallel` | 3 | 1台のスマホから同時に送る写真の数。**1〜6**。範囲外や不正な値は、アプリが1として扱う(安全側)。電波が弱い現場で失敗が増えるときは 1〜2 に下げる |

**現在の本番値:** `photoParallel` は 2026-10-12 に 3 → **4** へ変更済み(反応速度の改善策A②)。設定画面の「通信診断」で効果を測る。コードの既定値(3)は変えていない。
| `photoChunkChars` | 90000 | 小分け送信(旧方式)の1回あたりの文字数。通常は変えない |
| `photoMaxBytes` | 600000 | 写真1枚の最大バイト数 |
| `photoMaxPerItem` | 5 | 1項目あたりの写真の上限枚数 |

- Config の値を変えたら、第1章のとおり反映まで約1分かかります。

## 4. 写真ファイルが Drive に残る場合(孤児ファイル)

- 通常は、写真の保存に失敗したり、同じ写真が二重に届いたりしたときは、サーバーが後から作ったほうのファイルを自動でゴミ箱へ入れます。
- ただし、サーバーの実行が途中で強制終了された(6分を超えた等)場合は、ゴミ箱に入らないファイルが残ることがあります(SPEC P-37。自動掃除はしません)。
- 見分け方: Drive の `photos/…` 配下のファイル名は `{recordId}_{itemId}_{side}_{photoId}.jpg` です。スプレッドシートの `Photos` シートに同じ `photoId` の行が無いファイルは、記録に使われていないファイルです。確認のうえ手で削除して構いません(`Photos` に行があるファイルは消さない)。
- サムネは `thumbs/{photoId}.jpg` です。本体と同じ `photoId` で判断します。

## 5. 同じ名前のフォルダが2つできていたとき

- 現場・階・日付のフォルダを、同時に届いた写真が同時に作ると、まれに同じ名前のフォルダが2つできます。
- アプリは以後、**作成日時がいちばん古いフォルダ**を使います。写真はファイルIDで管理しているので、表示や PDF には影響しません。
- 空のほうのフォルダは、不要なら削除して構いません(中にファイルがあるときは、どの記録の写真か `Photos` で確認してから)。

## 7. 現場の追加・完了と名簿の書き込み(Claudeに依頼する運用)
シートを責任者が直接書き換えると転記ミスの元になるため、責任者が情報をClaudeに渡し、Claudeがシートへ書き込む。Claudeは行を完全削除しない。

### 7-1. 現場を追加するときに渡す情報
| 項目 | 必須 | 例・補足 |
|---|---|---|
| 現場名 | 必須 | アプリに表示される名前 |
| 階の選択肢 | 必須 | 表示順。例 `基礎,1階,2階,3階,屋上` |
| 元請会社名 | 必須 | 元請向けPDFの「元請会社」に出る |
| 主担当QA | 必須 | 既存のQA名簿から選ぶ(資格者のみ) |
| 副担当QA | 任意 | 指定がなければ責任者 |
| 職長 | 必須 | 氏名・班名・会社名(他社の場合)・言語(日本語/インドネシア語)。副職長がいれば同様に |
| 工区 | 任意 | 例 `東,西`。なければ工区なし |
| 住所・着工日・竣工予定 | 任意 | |
- 新規の人(名簿にいない人)は、氏名(同姓同名は区別できる表記)・役割(職長/QA)・会社名・言語を渡す。QAは資格者かどうかも。
- Claudeが書き込んだあと、現場ごとのQR(参加用)と、新規の人の招待コード発行が必要な人を報告する。招待コードは責任者がアプリから発行する(72時間・1回限り)。

### 7-2. 現場が完了したとき(閉鎖)
削除せず閉鎖する。渡す情報は「現場名」と「完了日」だけ。
1. 未完了の記録(下書き・提出中・差し戻し中など)が残っていないことをClaudeが確認する。残っていれば報告して止まる。
2. Sites: status を closed、endDate に完了日、updatedAt を更新。
3. Assignments: その現場の担当をすべて active=FALSE、validTo=完了日にする。職長・QAの画面から現場が消える。
4. 検査記録・写真・PDF・Eventsは残す。責任者は閉鎖後もアプリで閲覧できる(「閉鎖中」の印が付く。新規記録・参加申請は不可)。
5. 人(Users)は閉鎖では変更しない。退職などで使わせない場合は、別途「無効化」を依頼する。
- 再開する場合は、status を active に戻し、担当を作り直す(Claudeに依頼)。

### 7-2a. 検査項目(Items)を変えるとき
検査項目の変更もClaudeに依頼する(2026-10-12決定)。変えられるのは、これから作る記録の項目だけ(既存記録は作成時のまま)。
| やりたいこと | 渡す情報 | Claudeが行うこと |
|---|---|---|
| 項目を足す | 項目文(日本語)、グループ、段階(打設前/脱枠後)、入力する人(両方/職長のみ/管理者のみ)、重点項目か、許容(±mm)、実測値入力(なし/任意/必須)と最少測定点数、表示位置 | 新しいitemIdで行を足す。インドネシア語は訳案を付けて報告 |
| 出す・出さない | itemIdまたは項目文 | activeを切り替える |
| 並び順 | itemIdと新しい位置 | seqを変える |
| 誤字訂正(意味は変えない) | 直す項目と正しい文 | 同じ行の文を直す |
| 意味を変える | itemIdと新しい文 | 新しいitemIdで行を足し、古い行をactive=FALSEにする |
- 書き込み前の確認: 許容があればmeasureは任意以上/measure=requiredならminMeasuresを入れる/同じgroupKeyのグループ名は同じ。
- インドネシア語は暫定訳。追加・変更したら、わかる人に確認してもらう。反映まで最大約1分。

### 7-3. 間違って登録したとき
Claudeは削除せず、閉鎖(現場)・無効化(人)で使えなくする。物理的な行削除が必要なときだけ、責任者が手動で行う(必要な行はClaudeが一覧にする)。

### 7-4. 制約
- Claudeがシートに書き込めるのは、責任者のPCのClaudeデスクトップアプリがオンラインで、シートにログインしたブラウザが使えるときだけ。
- シートの変更がアプリに反映されるまで最大60秒かかる(§1)。

## 8. 出来形検査(版1.9)を既存の本番に入れる手順
(SPEC 版1.9 §2.6.1b・§6.8。ユーザー決定 2026-10-14)

版1.9で「出来形検査(脱型後。`stage=post_demold`)」が加わりました。**既存のスプレッドシートには、新しい検査項目(i50〜i69)も、設定 `enabledStages` の新しい既定(`pre_pour,post_demold`)も、自動では入りません**(`setupSheets` は既存の値を上書きしないため)。次の順番で行ってください。**順番は守る**こと(特に⑤は③の後)。

| 順 | 作業 | 誰が・どこで | 補足 |
|---|---|---|---|
| ① | バックエンドを配る | Apps Script のエディタ | `backend/` の最新(特に `Schema` `Seed` `Code` `Authz` `Records` `Report` `Notify`)を貼って上書きし、「デプロイを管理」→ 新バージョンでデプロイ(**URLは変わらない**) |
| ② | フロントを配る | 静的ホスティング | `SW_VERSION` を上げた最新版を公開(端末が「更新があります」を出す) |
| ③ | **項目を追加する** | Apps Script のエディタ | 関数 **`addMissingSeedItems`** を選んで「実行」(下記) |
| ④ | 古い端末を止める(必要なら) | Config シート(Claudeに依頼) | 古い端末が出来形を「打設可」と表示しないよう、必要なら `minClientVersion` を新しい版に上げる。上げると古い端末は「更新してください」になる |
| ⑤ | **出来形を使えるようにする** | Config シート(Claudeに依頼) | `enabledStages` を `pre_pour,post_demold` にする。反映は約1分後(急ぐときは `clearRefCache` を実行) |

### ③ `addMissingSeedItems` について
- 項目の初期値(`Seed.gs` の `SEED_ITEMS`、i1〜i69)のうち、**Items シートに itemId が無い行だけ**を末尾に足します。**既存の行は変更・削除しません**(文言や有効/無効を手で変えていても、そのまま)。Config も触りません。
- 実行するとログ(「実行ログ」)に `追加した項目(20件): i50, i51, …, i69` と出ます。**もう一度実行しても何も変わらず**、`追加する項目はありません(0件)` と出ます(何度実行しても安全)。
- 追加される項目: 出来形 i50〜i57(8項目)と、打設前 i58〜i69(12項目)。すべて有効(`active=TRUE`)・重点なし(`key=FALSE`)です。写真を必須にする項目(重点)は、責任者が決めてからClaudeに依頼してください(SPEC §2.6.2 の手順)。
- これは Apps Script のエディタから実行する関数で、アプリ(Webアプリ)からは呼べません。実行後、Items の参照キャッシュは自動で捨てられます。
- 初回の `setupSheets` で作った新規のスプレッドシートには、最初から i1〜i69 が入っているので③は不要です(実行しても0件)。

### ⑤を③より先にしない理由
出来形の項目が無いまま `enabledStages` に `post_demold` が入ると、項目のない出来形の記録ができてしまいます。そのためサーバーは「その段階の有効項目が0件」のときは `createRecord` を `STAGE_NOT_ENABLED` で断ります(記録は作られません)が、現場の職長が「出来形を選べるのに作れない」状態になるので、必ず③→⑤の順にしてください。

### 入れた後の確認
1. Items シートの末尾に i50〜i69 の20行が増えている(i1〜i49 は変わっていない)。
2. アプリで「新しい記録」を開くと、段階に「打設前」「出来形」が出る(約1分後。出ないときは `clearRefCache`)。
3. 出来形で記録を作ると、項目が **8つ**(i50〜i57。解体時のコンクリート破損〜出来形 段差)。打設予定日時の欄は無い。
4. 打設前で**新しく**記録を作ると、項目が **28**(従来の16+新規12)。**既に作ってある打設前の記録は16項目のまま変わらない**(記録は作成時の項目で固定されるため)。
5. 出来形の記録には「打設を止める」が出ない。最終状態は「打設可」ではなく「出来形確認済」。
6. 元請提出用PDFは、見出しが「型枠工事 出来形検査記録」、ファイル名が `現場名 階 ロット_出来形_v1_日時.pdf`(打設前は `_打設前_`)。
7. 通知メールの件名は、出来形のとき末尾に ` 出来形` が付く(例 `[型枠検査] 提出 A現場 2F 出来形`)。

### 補足
- 同じ現場・階・工区・ロットでも、打設前と出来形は**別の記録**として1件ずつ作れます。互いの状態には影響しません。
- 出来形は、職長の自主検査 → 品質管理者の検査 → 元請に提出(元請サイン記録)で、打設前と同じ流れです(PINの再入力も同じ)。違いは、打設予定日時と時間ルール(自主検査の締切など)を使わないこと、「打設を止める」ができないこと、最終状態の名前だけです。提出後に誰も確認しない時間の通知(30分・60分)は出来形にも働きます。
- 出来形を承認(出来形確認済)した後に取り消す操作はありません。間違って承認したときは、同じ場所で「再検査」の記録を作ります。
- i48・i49(旧案の出来形2項目)は無効のまま残してあります。i48(はらみ・段差)は i56・i57 と内容が重なるため、有効化は勧めません。i49(開口部の位置・大きさ)に当たる項目は i50〜i57 に無いので、必要なら有効化して構いません。
- 元に戻したいとき: `enabledStages` を `pre_pour` に戻せば、新しい出来形の記録は作れなくなります(作成済みの出来形の記録は残ります)。項目は削除せず、使わない項目の `active` を `FALSE` にします。

## 9. GASの起動待ち対策 keepWarm(版1.10)
(SPEC §6.7a・§2.14。ユーザー決定 2026-10-17)

しばらく使っていないあとの最初の操作が遅いのは、GAS(Webアプリ)の起動待ちが一因と考えられます。**数分おきに軽い読み取りだけをする時間トリガーを置いて、起動待ちを減らせるか試す**仕組みです。**効果は未検証です。** トリガーの実行環境と Webアプリの実行環境が同じである保証はなく、効かない可能性があります。下の「効果の確認」で測り、差が出なければ外してください。

### 導入手順(責任者が1回だけ)
1. バックエンドを最新にする(`backend/` の `Schema.gs` `Seed.gs` ほか。DEPLOY.md の手順で貼り替え、「デプロイを管理」から新バージョンでデプロイ)。トリガーの設置自体はデプロイとは別の操作です。
2. 間隔を変えたいときだけ、Config シートの `keepWarmMinutes` を書き換える(Claudeに依頼。既定は **5**(分)。使えるのは **5 / 10 / 15 / 30**)。行が無い古いシートでは、エディタで関数 `setupSheets` を実行すると、不足している `keepWarmMinutes`(5)だけが足されます(既存の行・値は変わりません)。それ以外の値(1・数字でない値・31以上など)は **5分** になり、実行ログにその理由が出ます。1分ごとは使いません。
3. Apps Script のエディタを開き、上部の関数のプルダウンから **`installKeepWarmTrigger`** を選んで「実行」する。
4. **初回は承認画面が出ることがあります。** 「権限を確認」→ 使っているアカウントを選ぶ →(「このアプリは確認されていません」と出たら「詳細」→「(プロジェクト名)に移動」)→「許可」。承認が済むと実行が始まります。
5. 実行ログに `OK: keepWarm を5分ごとに設置しました`(分は設定どおり)と出れば完了です。
6. 確認: エディタ左の時計アイコン「トリガー」を開き、関数 `keepWarm`(時間主導)が **1本だけ** あること。`escalationTick` と `dailyMaintenance` は別のトリガーで、そのまま残っています。

- **何度実行しても1本のままです**(実行のたびに、`keepWarm` のトリガーだけを先に消してから作り直します)。`setupTriggers` を実行しても `keepWarm` は消えません。コードの貼り替え(デプロイ)でもトリガーは消えません。
- トリガーは実行したアカウント(スクリプトの所有者)のものです。別のアカウントで実行すると、そのアカウントのトリガーになります。
- 間隔を変えるときは、`keepWarmMinutes` を直してから `installKeepWarmTrigger` をもう一度実行します。
- `keepWarm` はエディタの関数の一覧にも出ますが、誰が実行しても **Config・Items・Sites を読むだけで何も書きません**(ロックも取らず、Events・Idem・Drive・メールにも触れません。名簿・端末・担当は読みません)。

### 解除手順
1. エディタの関数のプルダウンから **`removeKeepWarmTrigger`** を選んで「実行」する。
2. ログに `OK: keepWarm のトリガーを1本削除しました` と出る(0本なら元から無い)。「トリガー」画面から `keepWarm` を手で削除してもかまいません。
3. `escalationTick` と `dailyMaintenance` は消えません(消えていたら `setupTriggers` を実行)。

### 効果の確認(導入の前後で比べる)

### クォータ(上限)の注意
- Apps Script には、1日あたりのトリガーの合計実行時間の上限があります(個人のGoogleアカウントは約90分/日、Workspace は約6時間/日が目安。**最新の値は公式の Quotas で確認してください**)。
- 既定の5分ごとは、1日288回 × 1回あたり約1〜2秒 = **約5〜10分/日** の見込みです。`escalationTick`(5分ごと)と合わせても余裕はありますが、間隔を詰める場合は、エディタの「実行数」画面で `keepWarm` の実行時間の合計を確認してください。
- 時間主導トリガーは1分に1回までです。そのため1分ごとは使わず、最短は5分にしています。
- `keepWarm` が失敗しても失敗通知メールが増えないよう、中で例外を握りつぶしています。動いているかは、エディタの「実行数」画面で `keepWarm` の行が5分おきに並ぶことで見ます。

## 10. 元請PDFをA4で作る(doc方式)の導入と見た目の確認(版1.10.1。実測の表示の確認は版1.11.0で追加)
(SPEC §10.5・§10.6・§12.7。ユーザー了承 2026-10-17。実測の表示は SPEC §10.2d・REAL-PDF-06。ユーザー依頼 2026-10-20)

**背景**: 今の元請PDFの作り方(HTML方式)は、用紙の指定が効かず**レターサイズ(215.9×279.4mm)**になります。そこで、用紙をA4・余白12mmと明示できる **Googleドキュメント経由の作り方(doc方式)** を追加しました。**既定は今までどおり HTML方式のまま**です(Config `reportEngine` = `html`)。doc方式の見た目が良いと確認できてから、既定を変えるかどうかを決めます(既定の変更は別の版です)。

**安全策**: doc方式が途中で失敗しても(承認が未了・Googleの上限・画像の問題・時間切れなど)、**自動でHTML方式に切り替わってPDFは必ずできます**。画面は変わらず、止まりません。切り替わったかどうかは「6. フォールバックしていないことの確認」で見ます。

**見た目は実際のGoogleでしか確認できません。** 自動テストは用紙・余白・写真の枚数・改ページの数・表の列幅といった「数値」までしか確かめていません。下の手順で、責任者が1件の記録を実際に見て確認してください。

### 1. 前提: 承認が済んでいること
`docs/DEPLOY.md` の「3-4a」(エディタで関数 **`checkReportEngine`** を1回実行 → 承認 → 新バージョンでデプロイ)が済んでいること。実行ログに `OK: doc 方式の変換に成功しました(A4 595.28×841.89pt)` と出ていれば前提を満たしています。

- `checkReportEngine` は試験用の1ページ文書を作ってPDFにし、すぐゴミ箱に入れるだけです。シート・Config・記録・PDFには何も書きません。何回実行しても構いません。
- 承認が済んでいないと、doc方式は「承認が必要」で失敗し、HTML方式で作られます(エラーにはなりません)。

### 2. 確認用の記録を用意する
打設前でも出来形でもかまいません。次を満たす記録を1件、`qa_ok`(元請待ち)または `approved` にします。
- **写真が5枚以上**(1ページ4枚+次のページに1枚、を見るため)
- **NG項目が1つ以上**
- **図面(確認箇所の書き込み)が1枚**
- **職長コメントと管理者コメントが入っている**(別の列・別の行で出ることを見るため)
- **実測が入った項目がある**(版1.11.0。下の「5a. 実測の表示の確認」用)。許容を超える値と、許容ちょうどの値を入れておきます。

### 3. doc方式で生成する
1. Claude に「Config の `reportEngine` を `doc` にして」と依頼する(約1分で反映します。Config は直接編集しても約1分で効きます。§1 参照)。
2. アプリでその記録の画面(S08)を開き、PDFを生成する。**押してから完了までの時間を書き留める**(下の表)。

### 4. 用紙を見る

### 6. フォールバックしていないことの確認
次のどちらかで確認します。
- **Drive**: そのPDFを右クリック →「詳細」(ファイル情報)の**説明**が `engine=doc` になっている。`engine=html (fallback from doc: …)` なら doc方式が失敗してHTML方式で作られています。`…` の理由(先頭100文字)を設計担当へ伝えてください。
- **Events シート**: `kind` が `report_generated` の最新の行の `detail` に `"engine":"doc"` がある。フォールバックしたときは `"engine":"html","fallbackFrom":"doc","fallbackReason":"…"`(理由は先頭200文字)になります。

### 補足(運用上の注意)
- doc方式は、PDFを作るたびに Drive の「マイドライブ直下」に一時文書 `_tmp_report_{記録ID}_{日時}` を作り、PDF変換のあと**すぐゴミ箱に入れます**(完全削除はしません)。ゴミ箱に入った文書は誰にも共有されません。
- 一時文書の作成には Drive・Docs の呼び出しが多く、HTML方式より時間がかかる見込みです(**所要時間は未計測**)。写真が多い記録(60枚近く)で80秒を超えると、HTML方式に自動で切り替わります。
- 元請に渡すPDFのファイル名・保存先・共有設定・版(v1, v2…)は、どちらの方式でも同じです。
