# 運用メモ(責任者・管理者向け)

DEPLOY.md は初回の設置手順、このファイルは「動き始めたあと」の運用で気をつける点です。
(SPEC 版1.4 §2.15・§5.4.4・§7.3 に対応)

## 1. スプレッドシートを直接編集したときの反映時間

| シート | 直接編集の反映 |
|---|---|
| **Config(設定)・Items(項目マスタ)・Sites(現場)** | **約1分後(最大60秒)** |
| Users・Devices・Assignments・Memberships・Absences(名簿・端末・担当・参加・不在) | すぐ(次の操作から) |
| Records・RecordItems・Photos・Notes・Events・Idem・Invites・Reports | すぐ(通常は手で編集しない) |

- **Config / Items / Sites を直接編集したら、反映まで約1分かかります。** 編集した直後に画面を開いても、古い設定(例: 写真の上限枚数、項目の文言、現場の状態)が表示されることがあります。1分ほど待ってから、アプリを開き直してください。
- 名簿(Users)・担当表(Assignments)・不在(Absences)・端末(Devices)の変更は遅れません。ユーザーの停止、担当の外し、端末の登録解除は次の操作から効きます(権限の判定にはキャッシュを使いません)。
- 現場の「合言葉(joinKey)」は遅れません。アプリの「合言葉を更新」でも、シートで直接書き換えても、更新後すぐに古い合言葉は使えなくなります。
- 急いで反映させたいとき: Apps Script のエディタで関数 `clearRefCache` を選んで「実行」すると、キャッシュをすぐ捨てます(再認可の画面は出ません。ログに「OK」と出ます)。
- 現場を閉鎖(`status=closed`)した直後の約1分間は、まだ記録の作成が通ることがあります。確実に止めたいときは1分待ってから現場の運用を止めてください。
- アプリが書き込む設定(例: 現場の写真フォルダIDの初回記入、合言葉の更新)は、書いた直後にキャッシュを捨てるので遅れません。

## 2. バージョン1.4への更新手順(写真送信の高速化)

1. Apps Script のプロジェクトに、新しいファイル **`RefCache`**(`RefCache.gs`)と **`PhotoUpload`**(`PhotoUpload.gs`)を追加し、`backend/` の中身を貼る。
2. 既存の `Code` `Repo` `Schema` `Seed` `Photos` `Admin` `Membership` を `backend/` の最新の中身で上書きする(DEPLOY.md の3-3のファイル一覧は、この2ファイルを加えた16ファイル)。
3. エディタで `setupSheets` を1回実行する。Config に不足している設定 **`photoSingleMaxChars`(1200000)** と **`photoParallel`(3)** の行が追記される。**既存の行・値は上書きしない**ので、設定済みの値は変わらない。実行しなくても、値が無いときは既定値で動く。
4. 「デプロイを管理」→ 既存のデプロイを編集 → バージョン「新バージョン」→ デプロイ(**URLは変わらない**)。
5. 写真を1枚撮って、送信が数秒で終わることを確認する。

## 3. 写真まわりの設定(Config)

| キー | 既定 | 意味・注意 |
|---|---|---|
| `photoSingleMaxChars` | 1200000 | 1枚を1回で送るときのデータ(base64)の最大文字数。4の倍数。`photoMaxBytes` を上げるときは `ceil(photoMaxBytes ÷ 3) × 4` 以上にする(例: 800000バイト → 1066668 以上)。下回っても動くが、アプリが小分け送信になって遅くなる |
| `photoParallel` | 3 | 1台のスマホから同時に送る写真の数。**1〜6**。範囲外や不正な値は、アプリが1として扱う(安全側)。電波が弱い現場で失敗が増えるときは 1〜2 に下げる |
| `photoChunkChars` | 90000 | 小分け送信(旧方式)の1回あたりの文字数。通常は変えない |
| `photoMaxBytes` | 600000 | 写真1枚の最大バイト数 |
| `photoMaxPerItem` | 5 | 1項目あたりの写真の上限枚数 |

- Config の値を変えたら、第1章のとおり反映まで約1分かかります。

## 4. 写真ファイルが Drive に残る場合(孤児ファイル)

- 通常は、写真の保存に失敗したり、同じ写真が二重に届いたりしたときは、サーバーが後から作ったほうのファイルを自動でゴミ箱へ入れます。
- ただし、サーバーの実行が途中で強制終了された(6分を超えた等)場合は、ゴミ箱に入らないファイルが残ることがあります(SPEC P-37。自動掃除はしません)。
- 見分け方: Drive の `photos/…` 配下のファイル名は `{recordId}_{itemId}_{side}_{photoId}.jpg` です。スプレッドシートの `Photos` シートに同じ `photoId` の行が無いファイルは、記録に使われていないファイルです。確認のうえ手で削除して構いません(`Photos` に行があるファイルは消さない)。
- サムネは `thumbs/{photoId}.jpg` です。本体と同じ `photoId` で判断します。

## 5. 同じ名前のフォルダが2つできていたとき

- 現場・階・日付のフォルダを、同時に届いた写真が同時に作ると、まれに同じ名前のフォルダが2つできます。
- アプリは以後、**作成日時がいちばん古いフォルダ**を使います。写真はファイルIDで管理しているので、表示や PDF には影響しません。
- 空のほうのフォルダは、不要なら削除して構いません(中にファイルがあるときは、どの記録の写真か `Photos` で確認してから)。

## 6. 性能の実測記録(SPEC §12.6。実GAS・ブラウザからの手動測定)

| 日付 | 条件 | 結果 |
|---|---|---|
| 2026-10-08(1.4系の反映前) | 写真約300KB(模様のみ=圧縮しにくい最悪ケース)を1枚、90KB×5分割 | 約35秒/枚。5枚で約4〜5分 |
| 2026-10-10(1.5.0反映後) | 同じ写真10枚、単発送信・3並列 | 10枚で38.6秒(同時最大3)。ping 約1.15秒、me 約1.6秒 |

- 実際の現場写真は、模様のみの試験画像より圧縮されるため、1枚あたりの容量はこれより小さくなる見込みです(未測定)。
- 目標(PERF-03: 10枚で約40秒以内)は満たしています。PERF-02(1枚約10秒)は、単独1枚での測定を別途行ってください。

## 7. 現場の追加・完了と名簿の書き込み(Claudeに依頼する運用)
シートを責任者が直接書き換えると転記ミスの元になるため、責任者が情報をClaudeに渡し、Claudeがシートへ書き込む。Claudeは行を完全削除しない。

### 7-1. 現場を追加するときに渡す情報
| 項目 | 必須 | 例・補足 |
|---|---|---|
| 現場名 | 必須 | アプリに表示される名前 |
| 階の選択肢 | 必須 | 表示順。例 `基礎,1階,2階,3階,屋上` |
| 元請会社名 | 必須 | 元請向けPDFの「元請会社」に出る |
| 主担当QA | 必須 | 既存のQA名簿から選ぶ(資格者のみ) |
| 副担当QA | 任意 | 指定がなければ責任者 |
| 職長 | 必須 | 氏名・班名・会社名(他社の場合)・言語(日本語/インドネシア語)。副職長がいれば同様に |
| 工区 | 任意 | 例 `東,西`。なければ工区なし |
| 住所・着工日・竣工予定 | 任意 | |
- 新規の人(名簿にいない人)は、氏名(同姓同名は区別できる表記)・役割(職長/QA)・会社名・言語を渡す。QAは資格者かどうかも。
- Claudeが書き込んだあと、現場ごとのQR(参加用)と、新規の人の招待コード発行が必要な人を報告する。招待コードは責任者がアプリから発行する(72時間・1回限り)。

### 7-2. 現場が完了したとき(閉鎖)
削除せず閉鎖する。渡す情報は「現場名」と「完了日」だけ。
1. 未完了の記録(下書き・提出中・差し戻し中など)が残っていないことをClaudeが確認する。残っていれば報告して止まる。
2. Sites: status を closed、endDate に完了日、updatedAt を更新。
3. Assignments: その現場の担当をすべて active=FALSE、validTo=完了日にする。職長・QAの画面から現場が消える。
4. 検査記録・写真・PDF・Eventsは残す。責任者は閉鎖後もアプリで閲覧できる(「閉鎖中」の印が付く。新規記録・参加申請は不可)。
5. 人(Users)は閉鎖では変更しない。退職などで使わせない場合は、別途「無効化」を依頼する。
- 再開する場合は、status を active に戻し、担当を作り直す(Claudeに依頼)。

### 7-3. 間違って登録したとき
Claudeは削除せず、閉鎖(現場)・無効化(人)で使えなくする。物理的な行削除が必要なときだけ、責任者が手動で行う(必要な行はClaudeが一覧にする)。

### 7-4. 制約
- Claudeがシートに書き込めるのは、責任者のPCのClaudeデスクトップアプリがオンラインで、シートにログインしたブラウザが使えるときだけ。
- シートの変更がアプリに反映されるまで最大60秒かかる(§1)。
